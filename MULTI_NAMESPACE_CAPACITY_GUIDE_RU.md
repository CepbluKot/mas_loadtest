# Поиск предельной частоты MAS через API: руководство для оператора и GLM

Это руководство относится к командам `capacity-plan`, `capacity-run` и
`capacity-status` файла `multi_namespace_benchmark.py` и конфигурации версии 4.
Они работают с MAS API. Доступ к `kubectl`, Kubernetes, Redis, PostgreSQL и
метрикам кластера на машине запуска не требуется. Другие команды того же
скрипта (`plan`, `run`, `resume`, `retry`, `summarize`) относятся к старому
фиксированному диагностическому прогону и имеют другую схему конфига.

## Что измеряется

Один запуск проверяет один из трёх видов нагрузки:

| `mode` | Одна джоба | Когда она успешна |
| --- | --- | --- |
| `workflow` | Вызов опубликованного Workflow через `POST /v1/workflows/run` или Chatflow через `POST /v1/chat-messages` в blocking-режиме | Для Workflow MAS вернул ID запуска и статус `succeeded`; для Chatflow — `event=message`, ID сообщения и непустой ответ |
| `rag_read` | Запрос к существующей базе через `POST /v1/datasets/<id>/retrieve` | В ответе есть массив `records` с числом записей не ниже `min_hits` |
| `rag_write` | Загрузка файла через `document/create_by_file`, затем опрос индексации созданного документа | Статус именно этого документа стал `completed` |

Режим `workflow` подходит для обычных задач и задач, которые вызывают LLM.
Для приложения типа Workflow задайте `inputs`; для Chatflow укажите
`app_type: "chatflow"` и текст `query`. Учитываются время и сбои всего вызова,
включая LLM. Chatflow должен быть опубликован и доступен через Service API.
`rag_read` по умолчанию использует keyword search без reranking; при явном
`retrieval_model` нагрузка зависит от выбранных настроек поиска.
`rag_write` создаёт **новый документ на каждую джобу** и не удаляет его.
Для записи используйте выделенную тестовую базу.

Бенч находит практическую границу для заданного набора ресурсов, файлов,
частот, таймаутов и ограничений конкуренции. Только по ответам API нельзя
установить точную внутреннюю причину ограничения MAS или измерить CPU, память
и длину очередей сервера. Для такого вывода нужны отдельные метрики.

## Что нужно подготовить

1. Python 3.12 и сетевой доступ с машины запуска к каждому `base_url`.
2. Уже созданные и опубликованные workflow либо существующие базы знаний.
3. Service API токен для каждого workflow или базы. Для `workflow`
   `console_token_file` необязателен: без него preflight проверяет `/v1/info`;
   с ним дополнительно проверяет опубликованный граф и привязку ключа.
   Для `rag_read` и `rag_write` Console токен не нужен.
4. Для `rag_write` — локальный файл, доступный машине запуска, и выделенная
   база для новых документов.
5. Приватный JSON-конфиг и локальные файлы токенов: владелец — запускающий
   пользователь, права `0600` или `0400`. Каталог результатов должен
   принадлежать этому пользователю; скрипт создаёт его с правами `0700`.

`namespace` в конфиге — метка target для отчёта. Скрипт не проверяет реальный
Kubernetes namespace через API MAS. Каждый target должен иметь свой уникальный
`base_url`; URL указывается как HTTP(S) origin без пути, параметров и токена,
например `https://mas-test.example.org`. Для HTTPS проверка сертификата
включена; для внутреннего CA задайте `ca_file`.

## Конфиг: верхний уровень

Полный актуальный пример: `multi_namespace_capacity.example.json` рядом с
этим руководством. Пути в нём вымышленные; подставьте реальные локальные пути.
Один конфиг запускает один `mode`. На практике удобнее хранить отдельные
конфиги для `workflow`, `rag_read` и `rag_write`; неиспользуемые списки ресурсов
можно удалить. Для выбранного режима соответствующий список обязателен и
непуст в каждом target.

| Поле | Обязательность и смысл |
| --- | --- |
| `version` | Обязательно `4`. |
| `mode` | Обязательно: `workflow`, `rag_read` или `rag_write`. |
| `results_root` | Обязательный корневой каталог результатов. Каждый новый `run-dir` должен лежать внутри него. |
| `min_rate_per_minute` | Обязательная начальная **общая** частота джоб в минуту по всем targets. Положительное целое. |
| `max_rate_per_minute` | Обязательная верхняя граница проверяемой общей частоты, не ниже минимума. Это граница эксперимента, а не объявленный предел MAS. |
| `rate_step_per_minute` | Обязательное положительное целое приращение после прошедшей ступени. Например, 10, 25, 40, 45 при минимуме 10, максимуме 45 и шаге 15. |
| `stage_seconds` | Обязательная длительность окна **подачи** запросов на каждой частоте, целое число не меньше 60. После окна скрипт дожидается всех джоб этой ступени. |
| `max_total_requests` | Обязательный суммарный бюджет запланированных джоб за прогон. Не включает preflight и GET-опросы индексации. Если следующая ступень не помещается целиком, она не запускается. |
| `max_inflight_per_namespace` | Обязательное положительное число одновременно выполняемых джоб на один target. Общий возможный пул потоков = число targets × это значение. Остальные джобы ждут в локальных очередях. |
| `request_timeout_seconds` | Обязательный положительный сетевой таймаут **каждого HTTP-вызова**: workflow POST, retrieval POST, upload POST или отдельного GET статуса. Не является общим дедлайном джобы. |
| `indexing_timeout_seconds` | Обязательное положительное время ожидания индексации **одного файла после upload**. Используется только в `rag_write`; отдельный GET может закончиться немного позже дедлайна. |
| `targets` | Обязательный непустой массив targets. |

Необязательные критерии оценки:

| Поле | По умолчанию | Влияние |
| --- | --- | --- |
| `min_success_ratio` | `0.99` | Минимальная доля успешных джоб после ожидания всей ступени. Проверяется и по всей ступени, и по каждому ресурсу. |
| `min_throughput_ratio` | `0.9` | Минимальное отношение наблюдаемого темпа завершения успешных джоб к темпу их начала. Нужен, чтобы растущее отставание не выглядело успехом. |
| `min_arrival_fidelity` | `0.95` | Минимальная доля запланированных джоб, которые действительно начали запрос к MAS внутри окна подачи. Если генератор не успел, предел MAS не определяется. |
| `max_p95_seconds` | Не задан | Необязательный предел p95 времени выполнения успешной джобы. Без него p95 измеряется, но не влияет на вердикт. |

Все доли должны лежать в `(0, 1]`. Применённые значения, включая значения по
умолчанию, выводятся командой `capacity-plan` в `criteria` и сохраняются в
`report.json`. Старые поля `rates_per_minute`, `max_stages`,
`min_completion_ratio` и `max_inflight` отклоняются. Число ступеней задаётся
минимумом, максимумом и шагом; отдельного `max_stages` нет.

## Target и ресурсы

Общие поля одного элемента `targets`:

| Поле | Смысл |
| --- | --- |
| `namespace` | Уникальная непустая метка для отчётов и очереди джоб. |
| `base_url` | Уникальный адрес MAS API target без пути, параметров и учётных данных. |
| `ca_file` | Необязательный путь к читаемому PEM-файлу внутреннего CA. |
| `console_token_file` | Необязательный путь к Console API токену. Если его нет в режиме `workflow`, доступность проверяется через Service API ключ запросом `/v1/info`; для запуска бенчмарка достаточно API-ключа workflow. |
| `workflows`, `rag_reads`, `rag_writes` | Список выбранного `mode`; в каждом target он должен содержать минимум один ресурс с уникальным `label`. |

Ресурс `workflows[]`:

| Поле | Смысл |
| --- | --- |
| `label` | Уникальная в пределах списка понятная метка для логов и отчёта. |
| `app_id` | ID опубликованного Workflow или Chatflow приложения. |
| `api_token_file` | Путь к его Service API ключу. |
| `app_type` | Необязательно, по умолчанию `workflow`. Значение `chatflow` переключает вызов на `POST /v1/chat-messages`; API `/v1/info` должен вернуть `mode: advanced-chat`. |
| `inputs` | Необязательный JSON-объект входных параметров; по умолчанию `{}`. Workflow получает его как есть, Chatflow передаёт его рядом с `query`. |
| `query` | Обязательный непустой текст только для `app_type: "chatflow"`. Отправляется в `POST /v1/chat-messages` с `response_mode: "blocking"` и `auto_generate_name: false`, чтобы одна джоба не запускала дополнительную генерацию названия диалога. |

Для Workflow preflight читает опубликованный граф и отклоняет приложение с
узлом `knowledge-retrieval`; когда задан Console токен, также проверяет
привязку Service API ключа. Для Chatflow preflight проверяет `/v1/info` и
ожидает режим `advanced-chat`. Успешный Chatflow вызов должен вернуть
`event=message`, `message_id` и непустой `answer`. Если одному приложению нужно
передавать разные входы или запросы, задайте несколько записей с разными
`label`.

Ресурс `rag_reads[]`:

| Поле | Смысл |
| --- | --- |
| `label`, `dataset_id`, `api_token_file` | Метка, ID существующей базы и путь к Service API ключу с доступом к ней. |
| `query` | Непустой поисковый запрос, одинаковый для повторов этой записи. |
| `top_k` | Необязательно, по умолчанию `5`: сколько результатов запросить у поиска по умолчанию. Положительное целое. |
| `min_hits` | Необязательно, по умолчанию `1`: минимальное число элементов `records` для успешной джобы. Можно задать `0`, если пустая выдача допустима. |
| `retrieval_model` | Необязательный полный объект настроек поиска MAS. Если он задан, скрипт передаёт его вместо модели keyword search по умолчанию; отдельный `top_k` тогда не используется. |

Ресурс `rag_writes[]`:

| Поле | Смысл |
| --- | --- |
| `label`, `dataset_id`, `api_token_file` | Метка, ID выделенной тестовой базы и путь к Service API ключу с правом загрузки. |
| `file_path` | Путь к читаемому локальному файлу. Те же байты используются для каждой повторной загрузки; имя отправляемого файла содержит ID прогона и номер джобы. |
| `indexing_technique` | Необязательно, по умолчанию `economy`; допустимы `economy` и `high_quality`. Должно совпадать с настройкой базы, иначе preflight остановит прогон. `high_quality` может задействовать embedding-модель MAS. |
| `process_rule` | Обязательный JSON-объект правила обработки MAS, например `{"mode": "automatic"}` для автоматической разбивки. Для иных режимов передайте параметры, которые принимает API MAS. |

Поле `max_file_bytes` удалено и отклоняется. Лимит загрузки самого MAS
остаётся. Бенч читает каждый файл целиком в память при загрузке конфига и
формирует multipart-запрос в памяти; оцените память машины запуска при больших
файлах и количестве ресурсов.

## Как распределяется нагрузка

Частота относится **ко всем targets вместе**. На каждой ступени планируется
`ceil(rate_per_minute × stage_seconds / 60)` джоб, интервалы подачи равны
`60 / rate_per_minute` секунды. Планировщик идёт по targets по кругу, затем
по ресурсам внутри выбранного target. Разница в числе запланированных джоб
между targets за ступень не превышает одной. Остаток переносится по кругу
на следующие ступени; даже при разном числе workflow targets получают примерно
равную общую долю.

Например, при 60 джобах/мин, окне 180 секунд и двух targets планируется 180
джоб: примерно по 90 каждому. Если у первого target два workflow, каждый
получит около 45, а единственный workflow второго — около 90. Это план
подачи, фактические старты могут запаздывать из-за занятых слотов.

Один поток выполняет одну джобу до её конца, включая ожидание индексации.
На target одновременно работают не более `max_inflight_per_namespace` джоб.
Остальные сохраняются в очереди своего target и ждут свободного слота; они
не отбрасываются. Targets могут работать одновременно. Первая частота должна
запланировать минимум по одному запросу на каждый ресурс каждого target:
плановое число джоб должно быть не меньше `число targets × наибольшее число
ресурсов в одном target`.

Следующая ступень начинается **после завершения всех джоб предыдущей**.
Пауза на разгребание очереди отражается в `drain_seconds`; плановая длительность
из `capacity-plan` не включает это время и API preflight.

## Команды и порядок запуска

Команды ниже выполняются из корня репозитория. `capacity-plan` читает локальный
конфиг и файлы, проверяет их форму и права, рассчитывает план; к MAS он не
обращается и каталога прогона не создаёт.
После распаковки поставки выполните те же команды из каталога
`mas-corporate-benchmark-kit`, заменив путь к скрипту
`scripts/k8s_scaling/multi_namespace_benchmark.py` на
`multi_namespace_benchmark.py`; пример JSON лежит рядом со скриптом.

```bash
cp scripts/k8s_scaling/multi_namespace_capacity.example.json /path/to/private/capacity.json
chmod 600 /path/to/private/capacity.json
python3 scripts/k8s_scaling/multi_namespace_benchmark.py capacity-plan \
  --config /path/to/private/capacity.json
```

Заполните реальные адреса, ID, пути токенов, `inputs`, запросы и файлы перед
`capacity-plan`. Для короткого прогона задайте `min_rate_per_minute` равным
`max_rate_per_minute`, выберите небольшую общую частоту и `stage_seconds` не
меньше 60. Соблюдайте условие покрытия всех ресурсов первой ступенью.

`capacity-run` сначала проверяет **все** выбранные ресурсы через MAS API.
Если preflight одного ресурса не проходит, измерение не начинается. Затем
создаётся новый приватный каталог результатов и начинается нагрузка.

```bash
python3 scripts/k8s_scaling/multi_namespace_benchmark.py capacity-run \
  --config /path/to/private/capacity.json \
  --run-dir /path/to/results/run-001

python3 scripts/k8s_scaling/multi_namespace_benchmark.py capacity-status \
  --run-dir /path/to/results/run-001
```

`run-dir` должен быть **новым** каталогом строго внутри `results_root`.
Повторное использование существующего каталога запрещено. `capacity-status`
во время работы или после обрыва процесса возвращает
`IN_PROGRESS_OR_INTERRUPTED` и уже записанные ступени; когда есть
`report.json`, возвращает итоговый отчёт. Эта команда не различает активный
и прерванный процесс. У capacity-режима сейчас нет `resume` и `retry`:
для нового измерения нужен новый `run-dir`. Повторение операции с неясным
исходом может создать дополнительный workflow run или документ.

JSON задаёт параметры нагрузки, но для запуска также нужны существующие
локальные файлы токенов и, в `rag_write`, файл фикстуры. В MAS должны быть
доступны выбранные базы и опубликованное приложение с включённым Service API.
Значения ключей храните отдельно от JSON с правами `0600` или `0400`.
`capacity-plan` не проверяет состояние MAS. Если `capacity-run` завершился
на preflight с `{"overall_status":"FAIL","error_type":"PreflightError"}`,
он ещё не создал `run-dir` и не отправил нагрузку; `capacity-status` по такому
пути читать нечего. Текущий CLI не выводит конкретную причину preflight.

## Как определяется результат ступени

После подачи всех запланированных запросов бенч **дожидается результатов всей
ступени** и только затем считает p50/p95/p99 и принимает решение. Время джобы
измеряется от фактического начала HTTP-работы до результата; ожидание слота
показывается отдельно как `queue_wait_seconds`.

1. `arrival_fidelity = started_in_window / planned`. Если она ниже
   `min_arrival_fidelity`, ступень получает `INCONCLUSIVE_GENERATOR`: клиент
   не подал запланированную нагрузку в окно. Это может означать занятые
   локальные слоты; предел MAS по этой ступени не объявляется.
2. `success_ratio = completed / submitted` после ожидания всех джоб.
   Требуется не меньше `min_success_ratio` глобально и для каждого ресурса.
3. `throughput_ratio` сравнивает наблюдаемый темп завершения успешных джоб
   с темпом их начала. Темпы считаются по промежуткам между 10-м и 90-м
   процентилями времён начала и завершения. Требуется не меньше
   `min_throughput_ratio` глобально и для каждого ресурса с достаточной
   выборкой. При менее трёх успешных джобах темп равен `null` и не проверяется.
4. Если задан `max_p95_seconds`, p95 успешных джоб также должен уложиться в
   этот предел глобально и на каждом ресурсе. Без лимита p95 всё равно
   сохраняется. p95 считается по завершённой выборке, не «на лету».
5. Каждый ресурс должен получить хотя бы одну джобу. Неизвестный исход
   отправленного POST или индексации останавливает поиск как неопределённый.

`completed_in_window`, `completion_ratio` и `completed_per_second` остаются
диагностическими показателями завершения **до конца окна подачи**. Они не
решают, прошла ли ступень: запрос в конце окна может нормально завершиться
позже. `drain_seconds` показывает, сколько прошло после конца окна до конца
всей ступени. Малые выборки и один успешный проход дают слабое основание для
рекомендаций о ёмкости; повторите измерение с достаточным числом джоб.

| `verdict` ступени | Значение |
| --- | --- |
| `PASS` | Все применимые критерии выполнены; можно пробовать следующую частоту. |
| `FAIL` | Нарушен критерий успеха, темпа или явный предел p95. Первая такая ступень останавливает поиск. |
| `INCONCLUSIVE_GENERATOR` | Клиент не начал нужную долю запросов внутри окна; предел MAS не определён. |
| `INCONCLUSIVE_COVERAGE` | Хотя бы один ресурс не получил ни одной джобы. |
| `INCONCLUSIVE_UNCERTAIN` | Исход POST или индексации неясен; автоматический повтор опасен дубликатом. |

Итоговый `capacity_status` требует совместного чтения с `stop_reason`:

| Значение | Интерпретация |
| --- | --- |
| `BRACKETED` | Есть последняя прошедшая (`last_passing_rate_per_minute`) и первая проваленная (`first_failing_rate_per_minute`) частоты. Практический интервал найден с точностью до шага. |
| `LOWER_BOUND` | Есть прошедшая частота, но нет доказанной проваленной. Причиной может быть достигнутый `max_rate_per_minute`, исчерпанный бюджет или неопределённая ступень; смотрите `stop_reason`. |
| `UNDETERMINED` | Нет ни одной прошедшей частоты; не объявляйте предел. |

Код возврата `0` у `capacity-run` означает наличие хотя бы одной прошедшей
ступени, **а не** обязательно найденный предел. Для автоматизации проверяйте
`capacity_status`, `stop_reason`, вердикты ступеней и фактические показатели.
Ошибки конфига или preflight дают код `2`; `UNDETERMINED` даёт код `1`.

## Файлы результата и связь джоб

Каталог создаётся с правами `0700`, файлы — `0600`.

| Файл | Содержание и назначение |
| --- | --- |
| `metadata.json` | Версия, режим, ID прогона, время создания и SHA-256 исходного конфига. |
| `context.json` | Метки и адреса targets, реальные ID workflow и баз; связывает безопасные метки с ресурсами MAS. |
| `events.jsonl` | Поток событий `stage_started`, `scheduled`, `dispatched`, `completed`, `stage_finished`, `run_finished`. Пишется во время прогона. |
| `stages.jsonl` | Одна полная запись на завершённую ступень: вердикт, причины, частота, время окна, очередь и агрегаты. |
| `tasks.jsonl` | Одна запись на завершённую джобу: `job_id`, target, ресурс, времена, статус и диагностические поля. Пишется после завершения всей ступени. |
| `report.json` | Итоговый JSON: применённый конфиг без секретов, все ступени, границы, итог и причина остановки. Появляется после штатного завершения. |

`job_id` объединяет записи в `events.jsonl` и `tasks.jsonl`; `namespace`,
`fixture`, `mode` и `resource_id` показывают, какая джоба обращалась к какому
ресурсу. `scheduled_at_utc` — время постановки по плану,
`started_at_utc`/`finished_at_utc` — фактическое выполнение,
`queue_wait_seconds` — ожидание локального слота. Времена UTC; длительности
считаются монотонными часами. `accepted` показывает успешное принятие HTTP
ответа, `success` — выполнение критерия джобы; это разные признаки.

Для Chatflow `tasks.jsonl` дополнительно записывает `app_type`,
`llm_total_tokens` и `llm_latency_seconds`, если MAS вернул usage metadata.
Текст LLM-ответа в отчёт не сохраняется.

Агрегаты ступени находятся также в `namespaces` и `resources`.
`planned` — число джоб по плану, `submitted` — число джоб с результатом,
`started_in_window` — фактические старты в окне, `completed` — успешные
джобы после ожидания всех результатов. `observed_start_rate_per_minute` и
`observed_completion_rate_per_minute` показывают измеренный темп успешной
выборки; `throughput_ratio` — их отношение, ограниченное сверху единицей.
Очередь отражают `peak_pending`, `peak_pending_by_namespace` и квантили
`queue_wait_*`. `p50_seconds`, `p95_seconds`, `p99_seconds` относятся к
успешным джобам и не включают ожидание локального слота.

Для workflow смотрите `workflow_status`; для чтения — `retrieval_hits`;
для загрузки — `indexing_status`, `upload_seconds`, `indexing_seconds` и
`indexing_polls`. `errors` группирует типы ошибок, `http_error_status`
заполняется, когда код ошибки POST известен. Содержимое токенов, `inputs`,
текст запроса RAG, байты файла и сырые ответы MAS не сохраняются. Но
`context.json`, `tasks.jsonl` и `events.jsonl` содержат внутренние адреса и
ID ресурсов: не публикуйте каталог без проверки.

## Инструкция для GLM или другой LLM-оператора

LLM управляет скриптом через shell и читает JSON; **нагрузку создаёт скрипт,
обращающийся к MAS API**, а не сама LLM. Перед началом оператору нужны:
адреса targets и их метки, режим, ID ресурсов, пути к существующим токенам,
входы workflow или запросы RAG или файлы, желаемый диапазон частот, шаг,
длительность ступени, предел конкуренции на target и каталог результатов.
Если обязательного значения нет, запросите именно его: не выдумывайте
токены, URL, ID и результаты.

Последовательность действий GLM:

1. Создать приватный конфиг версии 4 для **одного** режима; не помещать значения
   токенов в JSON, команды, промпт и итоговый отчёт. Использовать только пути
   к файлам токенов. Для следующего режима подготовить отдельный конфиг и
   новый каталог прогона.
2. Запустить `capacity-plan`, разобрать его JSON и проверить список targets,
   число ступеней, число возможных параллельных джоб и `criteria`. План не
   является доказательством доступа к живому MAS.
3. Запустить `capacity-run`. Preflight должен успешно проверить все ресурсы;
   иначе нагрузка не начинается. Не считать код возврата `0` доказательством
   найденного предела.
4. Пока прогон идёт, читать `capacity-status` и `events.jsonl`. После
   завершения использовать `report.json` как источник итогового статуса,
   `stages.jsonl` для сравнения ступеней, `tasks.jsonl` для ошибок отдельных
   джоб, `context.json` для сопоставления меток и ID. Не повторять POST с
   неопределённым исходом автоматически.
5. В отчёте указать режим, targets и ресурсы, диапазон/шаг, критерии,
   последнюю прошедшую и первую проваленную частоты, реальные темпы, p95,
   долю успеха, ожидание локальной очереди, причину остановки и ограничения
   интерпретации. Разделять локальную проверку скрипта, `capacity-plan` и
   реальные HTTP-вызовы MAS. `LOWER_BOUND` не выдавать за найденный максимум.

### Проверенный маршрут первого запуска

Если тестовых ресурсов ещё нет, сначала в MAS создайте и опубликуйте
приложение Workflow с простыми входами для обычных джоб и отдельный Chatflow
с LLM-узлом для модельного сценария. Для каждого приложения проверьте его
Service API ключ и состояние «Backend Service API»; это разные настройки.
Для RAG выберите выделенную тестовую базу, загрузите в неё синтетический текст,
дождитесь индексации и возьмите `dataset_id` из MAS. Убедитесь, что Service API
ключ Knowledge может читать эту базу. Для `rag_write` создайте отдельный
локальный синтетический файл; храните его вне репозитория и учитывайте, что
бенч будет загружать его повторно на каждой джобе. Доступ администратора в
веб-интерфейс сам по себе не является Service API ключом. Console API токен
нужен лишь для расширенной проверки обычного Workflow, когда задано поле
`console_token_file`; значения ключей не включайте в JSON.

В архиве поставки есть `synthetic_warehouse_ops.txt`. Его можно скопировать
в приватный каталог фикстур и указать в `rag_writes[].file_path`. Для проверки
`rag_read` сначала загрузите этот текст в тестовую базу, дождитесь индексации,
затем задайте запрос `WH-BENCH-204` и `min_hits: 1`. Архив не содержит
предзагруженную базу, ключи или реальные адреса MAS.

Для первого живого smoke-прогона подготовьте **три отдельных JSON** версии 4:
`workflow` с `app_type: "chatflow"` и коротким `query` для проверки LLM,
`rag_read` с запросом, который должен найти запись в тестовой базе, и
`rag_write` с небольшим синтетическим текстовым файлом. Для каждого JSON
задайте `min_rate_per_minute = max_rate_per_minute = 1`,
`rate_step_per_minute = 1`, `stage_seconds = 60`,
`max_total_requests = 1`, `max_inflight_per_namespace = 1` и отдельный новый
`run-dir`. Это **один запрос каждого вида**, а не тест предельной мощности.
При нескольких ресурсах первая ступень должна покрыть каждый ресурс;
увеличьте бюджет и частоту согласно выводу `capacity-plan`.

Запускайте команды из раздела «Команды и порядок запуска» для каждого JSON,
проверяя `report.json` и `tasks.jsonl` после `capacity-run`. Убедитесь, что
`workflow_status` успешен и, для Chatflow, есть метрики LLM при наличии их в
ответе MAS; у чтения проверьте `retrieval_hits >= min_hits`; у записи —
`indexing_status=completed` и отдельные `upload_seconds` и
`indexing_seconds`. Повторный `rag_write` создаёт **ещё один документ** даже
при тех же байтах фикстуры. При неизвестном результате upload сначала найдите
документ в MAS, затем решайте вопрос о повторе.

Живой smoke от 8 октября 2026 года на одном тестовом target прошёл во всех
трёх режимах: `rag_read` — 1/1, один найденный фрагмент, 0,299 с;
`rag_write` — 1/1, upload 1,281 с, индексация 1,378 с, всего 2,659 с;
LLM Chatflow — 1/1, `succeeded`, 45,254 с, задержка модели 43,625 с,
1786 токенов. Эти числа описывают **одиночные проверки работоспособности**.
`LOWER_BOUND` вместе с `stop_reason=max_rate_passed` при 1 запросе/мин
означает лишь, что единственная заданная частота прошла. Для одной джобы p95
совпадает с её временем и не даёт статистической оценки ёмкости.

### Когда Chatflow не проходит preflight

1. Проверьте, что приложение опубликовано, `app_type` равен `chatflow`,
   `app_id` соответствует именно этому приложению, а файл ключа читается
   локально. Новый ключ не требуется, если существующий действителен.
2. С **тем же Service API ключом** выполните только GET `/v1/info`. HTTP 403
   с `code=forbidden` и сообщением
   `The app's API service has been disabled.` означает, что у приложения
   выключен Service API, даже если ключ существует.
3. В карточке приложения MAS откройте сведения через значок/название
   приложения слева и проверьте переключатель «Backend Service API».
   Включение выполняйте только для нужного тестового приложения, затем
   повторите `capacity-run` с новым `run-dir`. Зелёный индикатор
   «In Service» на странице API Access в текущем интерфейсе не отражает
   реальное состояние этого переключателя.
4. Если `/v1/info` доступен, но preflight не проходит, проверьте его `mode`
   (`advanced-chat` для Chatflow, `workflow` для обычного Workflow), адрес
   target и соответствие токена приложению. Не выводите сам ключ в лог.

В описанном smoke существующий ключ Chatflow оказался действительным, но
Service API приложения был выключен. После включения **только этого** API
повторный запуск бенча завершился успешно. Это изменение состояния MAS,
а не поле JSON: исправить его одной правкой конфига нельзя.

## Частые ошибки настройки

| Симптом | Что проверить |
| --- | --- |
| `capacity-plan` не проходит | Права `0600` конфига и токенов, реальные локальные пути, версия 4, выбранный список ресурсов, положительные числа, покрытие всех ресурсов первой ступенью. |
| Preflight не проходит | Доступность MAS API, TLS/`ca_file`, токен именно этого приложения или базы, опубликованный workflow без Knowledge Retrieval, совпадение `indexing_technique` с базой. |
| `PreflightError` без подробностей и без `run-dir` | Нагрузка ещё не шла; проверьте Service API приложения через GET `/v1/info`, доступ базы через GET `/v1/datasets/<id>`, публикацию и переключатель «Backend Service API». После исправления создайте новый `run-dir`. |
| Ключ базы не удалось создать через Console API | Для preflight и нагрузки подходит существующий ключ Knowledge с доступом к нужной базе; проверьте его чтением GET `/v1/datasets/<id>`. Не считайте ошибку создания нового ключа ошибкой бенча. |
| `INCONCLUSIVE_GENERATOR` | Клиент не успевает начинать запросы; смотрите `arrival_fidelity`, `peak_pending`, `queue_wait_*` и `max_inflight_per_namespace`. Это ещё не доказательство предела MAS. |
| `INCONCLUSIVE_UNCERTAIN` | POST мог выполниться на сервере, даже если клиент потерял ответ; проверьте MAS по `job_id` и ресурсам перед новым запуском. |
| `LOWER_BOUND` после `request_budget` или `max_rate_passed` | Увеличение бюджета или верхней частоты требует нового прогона и нового каталога. Текущий отчёт содержит только нижнюю границу. |
| Медленный `rag_write` | Проверьте отдельно `upload_seconds`, `indexing_seconds`, `indexing_status`, таймауты и настройки базы. Отсутствие `max_file_bytes` не отменяет лимитов MAS. |

При сравнении разных прогонов сохраняйте одинаковые файлы, запросы,
workflow, число и настройки targets, длительность ступени и критерии. Иначе
разницу в результатах нельзя приписать только изменению частоты или MAS.
Шаблон итогового отчёта для человека и GLM:
[CAPACITY_REPORT_GUIDE_RU.md](CAPACITY_REPORT_GUIDE_RU.md).
