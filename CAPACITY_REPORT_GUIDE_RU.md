# Как составить итоговый отчёт по API-бенчмарку MAS

Это инструкция для человека или LLM, которая анализирует результаты команд
`capacity-plan`, `capacity-run` и `capacity-status` скрипта
`multi_namespace_benchmark.py` с конфигом версии 4. Настройка и запуск описаны
в [MULTI_NAMESPACE_CAPACITY_GUIDE_RU.md](MULTI_NAMESPACE_CAPACITY_GUIDE_RU.md).
Один каталог `run-dir` относится к одному режиму: `workflow`, `rag_read` или
`rag_write`. Для сравнения трёх режимов читайте три каталога и не смешивайте
их частоты в одну цифру производительности.

## Какие файлы читать

1. `report.json` — главный итог: `mode`, `criteria`, `capacity_status`,
   `stop_reason`, границы частоты и массив `stages`.
2. `stages.jsonl` — те же завершённые ступени в порядке записи. Полезен для
   анализа прерванного запуска, когда итогового `report.json` ещё нет.
3. `tasks.jsonl` — каждая завершённая операция, её `job_id`, метки, времена,
   статус, ошибка и поля конкретного режима. Записывается после завершения
   ступени; отсутствие строки во время работы не доказывает потерю джобы.
4. `events.jsonl` — постановка, начало и завершение операций, начало/конец
   ступеней. Связь с `tasks.jsonl` по `job_id`.
5. `context.json` — соответствие меток target/ресурса реальным адресам и ID.
   Используйте локально; перед передачей отчёта наружу удалите внутренние
   адреса и ID либо согласуйте их раскрытие.
6. `metadata.json` — ID прогона и хеш исходного конфига для проверки, что
   сравниваются ожидаемые запуски.

Если `capacity-run` завершился ошибкой preflight, каталог и `report.json` могут
вообще не появиться. В таком случае пишите «нагрузка не запускалась», а не
«нулевая производительность». `capacity-plan` проверяет локальный конфиг,
но сам по себе не доказывает доступность MAS.

## Порядок анализа

1. Зафиксируйте `run_id`, UTC-время, режим, число targets, их метки и список
   ресурсов. Укажите частоты `min_rate_per_minute`, `max_rate_per_minute`,
   `rate_step_per_minute`, окно `stage_seconds`, бюджет
   `max_total_requests`, `max_inflight_per_namespace` и таймауты.
2. Выпишите применённые пороги из `criteria`, включая значения по умолчанию:
   `min_success_ratio`, `min_throughput_ratio`, `min_arrival_fidelity` и
   `max_p95_seconds`. Значение `null` у p95 значит: квантиль измерен, но не
   решает вердикт. Не приписывайте конфигу порог, которого в нём нет.
3. Для каждой ступени выпишите `rate_per_minute`, `planned`, `submitted`,
   `started_in_window`, `completed`, `verdict`, `reasons`,
   `arrival_fidelity`, `success_ratio`, `throughput_ratio`, фактические
   `observed_start_rate_per_minute` и `observed_completion_rate_per_minute`,
   p50/p95/p99, ошибки и ожидание локального слота `queue_wait_*`.
4. Проверьте `namespaces` и `resources` каждой ступени. Общая частота делится
   между targets; её нельзя выдавать за частоту каждого target. Доля успеха
   и p95 по всей ступени не заменяют показатели отдельного ресурса. Ресурс
   без джобы означает недостаточное покрытие.
5. Сверьте ошибки агрегатов с `tasks.jsonl`: `namespace`, `fixture`,
   `resource_id`, `job_id`, `success`, `accepted`, `error`,
   `http_error_status`, времена и `queue_wait_seconds`. `accepted=true` ещё
   не означает успешного завершения. Для конкретной джобы найдите события
   в `events.jsonl` по `job_id`.
6. Укажите `capacity_status` вместе с `stop_reason`. `BRACKETED` даёт интервал
   между последней прошедшей и первой проваленной частотой. `LOWER_BOUND`
   означает лишь подтверждённую нижнюю границу, если проваленной частоты нет.
   `UNDETERMINED` не даёт подтверждённой нижней границы. При
   `max_rate_passed` бенч достиг только заданного потолка эксперимента.

## Поля по режимам

| Режим | Что обязательно сообщить | Как трактовать |
| --- | --- | --- |
| `workflow` | `workflow_status`, `duration_seconds`, ошибки и долю успеха; для Chatflow дополнительно `app_type`, `llm_total_tokens` и `llm_latency_seconds`, если MAS их вернул | Это время полного blocking-вызова. LLM и внешние зависимости входят в него; отсутствие usage metadata не означает нулевой расход токенов. |
| `rag_read` | `retrieval_hits`, `min_hits`, длительности, долю успеха и ошибки | Джоба успешна при числе записей не меньше `min_hits`. Уточните, был ли передан собственный `retrieval_model` или использован keyword search по умолчанию. |
| `rag_write` | `indexing_status`, `upload_seconds`, `indexing_seconds`, общее время, ошибки и число созданных документов | Успех наступает после `completed` для загруженного документа. Каждый повтор создаёт новый документ; количество GET-опросов индексации не входит в `max_total_requests`. |

При `INCONCLUSIVE_GENERATOR` изучите `arrival_fidelity` и `queue_wait_*`:
клиент не успел начать нужную долю запросов в окно. Это нельзя объявлять
пределом MAS. При `INCONCLUSIVE_UNCERTAIN` исход отправленного POST либо
индексации неизвестен; до повтора проверьте состояние задачи или документа в
MAS. `completed_in_window` и `completion_ratio` описывают только завершения
до конца окна подачи; ступень оценивается после ожидания всей выборки.

Малые выборки требуют отдельной пометки. Если успешных операций меньше трёх,
`throughput_ratio` не оценивается. При одной операции p95 совпадает с её
длительностью и не характеризует распределение задержек. Отчёт 1/1 при
1 запросе в минуту — подтверждение работоспособности API, а не найденный
максимум. Только API-данные также не показывают CPU, память, внутреннюю
очередь Celery или точную причину насыщения MAS; для этого нужны отдельные
метрики, которых в данном архиве результатов нет.

## Шаблон итогового текста

```text
Бенчмарк MAS: <дата и время UTC>, run_id <...>, режим <...>.
Контур: <число targets и их разрешённые к публикации метки>;
ресурсы: <метки workflow/баз без секретов>.
Нагрузка: <минимум>–<максимум> запросов/мин суммарно, шаг <...>,
окно <...> с, бюджет <...> джоб, максимум <...> одновременно на target.
Критерии: успех >= <...>, темп >= <...>, точность подачи >= <...>,
p95 <= <... или не задан>.
Итог: <capacity_status>, причина <stop_reason>.
Последняя PASS: <... или нет>; первая FAIL: <... или нет>.
Ступени: <для каждой частота, план/успех, фактический темп, p95,
ожидание слота, ошибки и verdict>.
Разрез по targets/ресурсам: <отличия и слабые места>.
По отдельным джобам: <workflow_status / retrieval_hits / indexing_status,
времена upload и indexing, токены LLM при наличии>.
Вывод: <что подтверждено данными>.
Ограничения: <малые выборки, прерывание, генератор, внешняя LLM,
отсутствие серверных метрик, несопоставимые конфиги>.
Следующий замер: <конкретная частота/шаг/бюджет/число повторов, если нужен>.
```

Для сравнения запусков укажите различия в файлах, запросах, графах workflow,
числе targets, длительности ступени, конкуренции и критериях. Не объясняйте
разницу одним лишь изменением частоты, если эти условия тоже изменились.
Содержимое `inputs`, запросов и LLM-ответов скрипт не сохраняет; не
восстанавливайте их догадками. В отчёт для внешней передачи включайте
агрегаты и безопасные метки, а исходные JSON/JSONL оставляйте в закрытом
контуре, пока не проверено отсутствие внутренних адресов и ID.
